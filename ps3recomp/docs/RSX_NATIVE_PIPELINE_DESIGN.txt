Problem
cellGcmSys.c synchronously dispatches methods to rsx_live_draw_method.
rsx_dispatch invokes its end sink inline. sink_end_impl ignores the supplied
state and uses global g.rsx/dc for fetch, resources and command recording.
Guest input spans and inline arrays are borrowed. Adding a worker without
changing these lifetimes makes subsequent state/memory writes race the draw.
On the producer side, geometry still retains the SPU ABI around typed kernels.
An independent result must cross both boundaries; a generic queue alone is
not a useful implementation deliverable.

Intended ownership graph
Title adapter: mesh inputs + pose generation + view generation + dependencies
    -> CPU geometry calculation with owned, typed results
    -> ordered publication of completed units
RSX capture: state + input versions/owned spans + operation sequence
    -> bounded queue of immutable draw/clear/transfer/signal operations
Graphics owner: resource lookup/update + barriers + D3D12 command recording
    -> existing submission/frame-resource lifetime
GPU completion -> retirement/reuse and applicable guest-visible completion

The SDK owns packet/lease/ordering mechanisms. The title adapter identifies
semantic game inputs and dependencies. No title addresses or assumptions
about image1014 belong in the generic queue or graphics protocol.

1. Sequence and completion types
Keep distinct: decoded operation, inputs captured/prepared, API commands
recorded, GPU work submitted, GPU fence completed, guest notification delivered.
Each operation carries a monotonically increasing sequence and relevant
dependencies. A recorded packet is NOT a completed GPU operation. Advancing
FIFO GET means command bytes have been consumed; it must not falsely retire
vertex/texture memory or turn all guest labels into generic GPU fences.
Classify each guest synchronization operation by the actual dependency it
represents. Keep the existing real completion semantics until each replacement
is proven. GPU-idle, callbacks, blit/resolve and CPU readback are explicit.

2. Immutable draw inputs
The recording stage receives an explicit semantic state view, never the live
dispatcher. Capture relevant render state, primitive/ranges, layout/frequency,
viewport/scissor, program identity/version, constants, texture/surface bindings
and all data that can change before use. Draw scratch belongs to its stage.
Program records must be immutable while referenced. Inline vertex bytes cannot
point into the dispatcher's reusable inline_data. Source indices/references
must be captured before the source can be rewritten. Existing vertex-pull
plans borrow spans until write(); queue only after ownership is established.

Do not memcpy the full rsx_dispatch per draw: it includes coverage and inline
scratch unrelated to most draws. Start with semantic records or changed blocks
and a private consumer state. Do not infer unchanged memory from unchanged
addresses/registers; program constants and resource content have versions too.

3. Memory and resource leases
A span is either owned by the packet/submission or protected by an explicit
lease that prevents the producer from rewriting it until its reader finishes.
A hash/version check alone is not a lease against a concurrent writer.
The capture boundary must have ordering that already makes the data readable.
Anticipatory reads overlapping earlier queued writes must be deferred or taken
after the relevant predecessor completes. GPU-produced images/buffers remain
resource handles with version/dependency information, not arbitrary RAM copies.
Texture source storage needs the same rule as vertices and constants.

The existing D3D12 frame resources retain upload data, descriptors and command
allocators until their GPU fence. CPU packet storage may retire earlier only
after its last CPU reader finishes. GPU-visible staging may not. Capacity is
bounded, exhaustion applies backpressure, and overflow never drops a draw.

4. Ordered consumer and special operations
Initially use one owner for mutable PSO/texture/surface caches, descriptors,
resource states, barriers and API recording. Capture/preparation must not
concurrently mutate them. Shared immutable compiled programs may be leased.
Clear, draw, transfer/resolve, flip and synchronization preserve stream order.
CPU reads/writes, movie overlays, resize, debugging/readback and shutdown need
an explicit ownership handoff or ordered operation. Draining a CPU stage is
different from waiting for the GPU; do not introduce a GPU wait at every draw.
Unsupported capture uses an ordered synchronous fallback after the necessary
boundary, never a concurrent call into the same caches.

5. Scheduling granularity
Queue complete ready units, accumulate several operations per notification,
and flush at dependency/latency/capacity boundaries. Do not require a whole
frame to finish before publishing anything: an upstream producer may itself
need a label generated by earlier work. Do not defer per-job completion to
the end of a batch without proving there is no intra-batch dependency.
Avoid a new task and join for each draw. Pure preparation workers consume
owned inputs; results are used only after validation against the ordered
consumer state, with fallback for stale/unsupported work. Introduce this pool
only after the primary ownership split. Worker budgets respect available
processors/affinity and retain an efficient single-thread path.

6. Native geometry boundary
Mesh identity and source format, pose/weights/palette, view/culling state and
destination/publication dependencies become separate arguments/results.
Do not use a cached SPU GPR/LS image as the native mesh result: it contains
temporary addresses, stack/return state, lane identity and publication state.
The existing typed skinning kernel is reusable arithmetic, not the whole job.
Classify the consumers of the remaining phases before moving normal/tangent,
transform or culling work. Preserve arithmetic/edge-case contracts and fall
back for unknown input formats before any partial output is published.
Keep simulation at its intended cadence; interpolation consumes stable pose
and camera snapshots. Skipping unchanged simulation is not interpolation.
